PHASE 6 — ⭐ PACT FIREWALL

This is arguably the most important engineering phase.

Goal

Nothing involving money becomes real unless it passes our rules.

Prompt
Continue building the existing PACT project.

Implement the PACT Firewall.

The PACT Firewall is a deterministic policy engine that validates every Deal Contract before it can proceed toward payment.

Important principle:

AI can propose.
PACT decides what becomes real.

Implement the following policy checks:

1. INVENTORY_CHECK

Verify every product has sufficient stock.

2. PRICE_VERIFICATION

Verify all product prices match the current Firebase catalog.

3. DISCOUNT_LIMIT

Verify the discount percentage does not exceed the merchant's configured maximum.

4. BUDGET_CONSTRAINT

Verify the final amount satisfies the buyer's budget if a budget was specified.

5. DELIVERY_CONSTRAINT

Verify the delivery estimate satisfies the buyer's requested delivery limit.

6. TRANSACTION_LIMIT

Check whether the transaction amount exceeds the merchant's auto-approved amount.

7. HUMAN_APPROVAL_GATE

If the amount exceeds the configured approval threshold, mark the deal as:

PENDING_APPROVAL

instead of automatically approving.

8. DUPLICATE_PROTECTION

Prevent duplicate payment attempts for the same approved deal.

9. PRODUCT_VALIDITY

Reject inactive or nonexistent products.

Each policy evaluation should return:

ruleName
status
PASS or FAIL
severity
explanation

The final Deal status should be:

VALIDATED
REJECTED
PENDING_APPROVAL

Create a visually impressive PACT Firewall screen.

Show every rule being evaluated.

Example:

✓ INVENTORY CHECK
PASS

✓ PRICE VERIFICATION
PASS

✗ DISCOUNT LIMIT
FAILED

Requested: 18%
Allowed: 10%

DEAL REJECTED

Create audit events for every policy evaluation.

The system must explain exactly why a deal was rejected.

Do not allow the frontend to bypass policy validation.

All critical validation must happen server-side.

Create a set of automated or repeatable test scenarios.

At minimum include:

1. SUCCESSFUL_DEAL

Buyer requests products.
Merchant has stock.
Discount is valid.
Deal passes validation.
Payment can proceed.

2. INVALID_DISCOUNT

Buyer requests a discount greater than the merchant policy allows.

Expected:
PACT Firewall rejects the deal.

3. OUT_OF_STOCK

Buyer requests more quantity than available.

Expected:
Deal is rejected or Merchant Agent suggests a valid alternative.

4. BUDGET_EXCEEDED

Merchant offer exceeds buyer budget.

Expected:
Merchant Agent attempts alternatives.
If no valid solution exists, the deal does not proceed.

5. DELIVERY_CONSTRAINT_FAILURE

Requested delivery time cannot be satisfied.

Expected:
Deal is rejected or alternative is proposed.

6. DUPLICATE_PAYMENT_ATTEMPT

Attempt to create payment twice for the same deal.

Expected:
Duplicate protection prevents multiple successful orders.

7. PAYMENT_FAILURE

Simulate or handle a failed Razorpay test payment.

Expected:
Deal remains unpaid.
System records the failure.
No false successful order is created.
